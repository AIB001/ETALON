# Selection, composition and legitimate bypass

An observed failure may concern a method's contents (S), when/how it is used (U),
or how revisions are proposed and checked (G). Inspect the relevant returned
evidence to distinguish them; do not rewrite all three because a task was slow.

If a bundle was available but no semantic read is recorded, its content effect
has not been measured. A file hash, catalog entry or import is not application.
If a host read a reference but its output does not use it, keep read/applied
separate. Preserve the raw call or output pointer alongside host attribution;
the SDK's MethodUse remains `host_reported`.

For a known operation, direct SDK/file access may be preferable. A skipped skill
with a correct result is a successful task; forcing adoption would change the
question. If lookup really blocks progress, a candidate can provide one precise
member/API and its inputs, verified in the actual installation. A wrong or stale
pointer is a counterexample. Smaller tool output alone does not prove lower
total input tokens or latency; missing timeout usage stays unknown.

Partial use identifies the actual section or script, with a reason for omitted
parts. Composition records the selected versions and which contribution each
made, not a synthetic all-or-nothing adoption flag. An empty selected-method
list is valid. Usage guidance has its own version and can remain unchanged when
S changes; there is no required global router or order of operations.

Compare a candidate against the original on the question that motivated it,
within existing authorization. Retain failures and no-change decisions. Keep
development data distinct from later independent tasks; host choice and task
quality matter independently of adoption rate. For costs, count generation and
use attempts, while separating historical costs from new processing and avoiding
double-counting nested timings. Do not fabricate a zero for missing telemetry.
