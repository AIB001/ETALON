# Engineering within the project's scope

Use the project's development instructions, file ownership and actual runtime
when changing an implementation or installing an adapter. This optional guide
does not grant a new resource budget or establish a product-wide workflow.
Project-specific development skills and instructions remain project resources;
they are not scientific methods in the ETALON catalog.

The [setup reference](../HOST_SETUP.md) describes `etalon.host export` and
`verify`. Export into a new directory from the actual intended interpreter.
Integrate deliberately with existing project configuration; do not overwrite
local instructions. `host-guides/` and `HOST_SETUP.md` are optional exported
references, not text concatenated into the default AGENTS/CLAUDE entry.

Keep source snapshots, dirty/untracked implementation, immutable evidence and
the environments required by active jobs. Do not upgrade a shared environment
or replace a running version as an incidental setup step. Tests should run with
the intended interpreter and record actual module paths, not just Git HEAD.
Package/export byte checks, MCP calls and native host decisions are different
evidence. Report untested hosts and unavailable telemetry explicitly.

For several related local checks, a bounded script can call actual SDK functions
and branch on their results. Preserve dependencies, per-item failures, original
refs, unknowns and measured costs. Independent reads may run concurrently where
the API permits. The script is editable by the host and is not a mandatory task
router, scientific workflow or substitute for execution/receipt checks.

Before scientific action, use the project's authoritative current status and
scope. Engineering maintenance, fixture tests and evidence retrieval alone do
not resume paused work, send CRO orders or prove a scientific improvement.
